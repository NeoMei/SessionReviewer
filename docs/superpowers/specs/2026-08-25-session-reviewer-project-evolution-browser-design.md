# SessionReviewer 项目脉络浏览器与精简输出设计

- 状态：已确认
- 日期：2026-08-25
- 适用平台：Obsidian Desktop on macOS / Windows，代码仓库中的普通 Markdown
- 取代：2026-08-25-session-reviewer-human-readable-ledger-navigation-design.md 的多文档导航方案

## 1. 背景

SessionReviewer 当前能够从长 Session 中提取项目状态、决策、时间线、用量和证据，并在代码目录与 Obsidian 之间同步。但真实使用表明，现有输出把同一件事拆散到首页、当前状态、时间线、演进图、决策目录、待办目录、Session 目录和多个索引中。信息虽然完整，却存在三个问题：

1. 用户必须先理解内部目录和实体模型，才能恢复项目上下文。
2. 相同内容在多个页面重复出现，页面多、入口多、阅读路径不明确。
3. 静态 Mermaid 和长 Markdown 只能展示，不能通过点击时间节点探索当时的背景、变化、决策和结果。

新设计不再优化旧页面，而是把产品重构为“项目脉络浏览器”：人类阅读默认只面对一个可交互页面和两个可编辑 Markdown 文件；机器证据、稳定 ID、哈希、cursor、revision 和同步状态进入隐藏账本。

本设计是对原始设计中“首版不提供 Obsidian 插件”边界的有意升级。CLI、账本和同步基础已经成立，现在增加轻量 Obsidian 桌面插件视图，用于承载纯 Markdown 无法提供的节点切换与内联编辑。

## 2. 目标

用户隔几天重新打开项目后，应能快速回答：

- 项目现在进行到哪里；
- 接下来最应该做什么；
- 项目经历了哪些关键转折；
- 某个时间节点为什么发生、改变了什么、如何验证；
- 哪些决策影响了当前方向；
- 还有哪些风险或未完成事项；
- 项目累计花费了多少时间、Token 和成本，各模型占比如何。

同时满足：

- 默认阅读目录中只保留两个 Markdown 文件；
- 项目目录与 Obsidian 两边都可编辑；
- 交互页面中的编辑最终写回 Markdown；
- 机器生成字段不可被普通编辑伪造；
- 旧项目可自动迁移且可恢复；
- macOS 与 Windows 均可安装和使用。

## 3. 输出结构

### 3.1 人类可读文件

正常阅读目录只显示：

~~~text
docs/session-review/
├── 项目回顾.md
└── 项目历史.md
~~~

Obsidian 映射目录显示同样两个文件：

~~~text
<Vault>/Projects/<project>/Session Review/
├── 项目回顾.md
└── 项目历史.md
~~~

项目回顾.md 是短小的当前态来源和无插件降级入口，包含：

- 项目名称与目标；
- 当前阶段和当前状态；
- 下一步；
- 风险与待办；
- 关键决策摘要；
- 最近验证；
- 指向项目历史.md 的链接。

项目目标、当前状态、风险和关键决策以项目回顾.md 为唯一人类可编辑来源。关键决策在该文件中保存完整的结论、原因和影响；页面可只展示摘要，但不能在其他文件维护第二份可编辑副本。

项目历史.md 是单一、逆时间排列的项目事件流，不按 Session 分目录。每个事件包含：

- 日期与事件标题；
- 事件类别；
- 为什么发生；
- 发生了什么；
- 结果和验证；
- 关联决策；
- 留下的问题或下一步。

事件使用不会在 Obsidian 阅读视图中显示的稳定标记保存身份。普通标题和正文保持自然中文，不暴露哈希、cursor、revision 或证据 ID。

项目历史.md 中的事件只通过稳定 ID 引用关键决策，决策标题由项目回顾.md 的规范条目解析。这样既能从节点跳转到决策，又不会出现两处修改同一决策的歧义。

### 3.2 隐藏机器数据

~~~text
docs/session-review/.session-reviewer/
├── ledger.json
├── conflicts/
└── backups/
~~~

- ledger.json 是版本化、同步到 Obsidian 的机器底账，保存 schema 版本、稳定实体身份、用量、价格、证据引用、同步元数据和内容关联。它从 Project 单向发布到 Vault 并校验哈希，不接受 Vault 侧人工修改，也不参与人类语义三方合并。
- conflicts/ 保存机器可读冲突记录，不在普通阅读目录制造冲突文档。
- backups/ 保存迁移前快照；默认只保留在 Project 本机、排除普通实体扫描、Git 提交和 Vault 发布。备份 manifest 记录恢复所需的相对路径与哈希，用户确认迁移无误后才能主动清理。

Obsidian 插件通过 Vault Adapter 读取隐藏数据。普通用户不需要直接打开或编辑这些文件。

## 4. 项目脉络浏览器

### 4.1 页面定位

Obsidian 插件注册独立的“SessionReviewer 项目脉络”视图。它不是把 Markdown 转成另一套不可编辑数据库，而是把两个 Markdown 与隐藏账本组合成一个可探索页面。

代码目录仍可使用任何编辑器直接修改两个 Markdown。完成现有 Project ↔ Obsidian 同步后，插件收到 Vault 文件变更事件并刷新页面。

### 4.2 页面骨架

页面由四层组成：

1. 项目头部：项目名、进行状态、同步状态和最后更新时间。
2. 恢复条：当前阶段与唯一推荐下一步，始终位于主内容上方。
3. 视角切换：项目演进、关键决策、投入统计。
4. 当前视角内容：根据用户选择更新，不把所有信息同时堆在一屏。

桌面端充分利用横向空间。项目演进视角使用左右双栏：

- 左栏为时间节点导航；
- 右栏为当前选中节点的详细信息；
- 两栏共同自然向下滚动；
- 小于约 860px 时退化为单栏，先节点列表、后节点详情。

### 4.3 项目演进视角

左侧默认显示最近五个关键节点，每个节点显示日期、事件类别、人类可读标题和一句“它让项目发生了什么变化”。

点击节点后，右侧原位切换：

- 节点标题和日期；
- 一句节点意义；
- 白话摘要；
- 为什么会走到这里；
- 这一节点改变了什么；
- 结果与验证；
- 关联决策；
- 留下的问题或下一步。

“打开完整项目历史”展开或进入可搜索的完整节点列表。节点切换不打开大量新文件，不改变当前滚动上下文。选中节点保存到 Obsidian workspace state，重新打开工作区时恢复。

### 4.4 关键决策视角

关键决策按时间逆序显示，只收录真正改变产品方向、实现边界或验收标准的决策。每项包含日期、结论、原因、影响范围和关联时间节点。

点击关联节点返回项目演进视角并选中对应节点。决策不是孤立卡片，而是项目因果链的一部分。

### 4.5 投入统计视角

顶部显示项目总耗时、总 Token、按公开百万 Token 标价计算的总成本和使用模型数量。

下方按模型显示：

- input、cached input、cache write、output、reasoning output 和 total tokens；
- Token 占比与成本占比；
- 输入、缓存和输出的公开百万 Token 单价；
- 单价来源和生效日期。

默认先显示简洁占比，展开后再显示完整核算明细。订阅额度不参与计算。

### 4.6 插件交付

Obsidian 插件与 Go 引擎保存在同一仓库的独立子目录，共享一份版本化数据合同，但各自构建。发布资产至少包含 manifest.json、main.js 和 styles.css，并与要求的最低 Obsidian 版本和 SessionReviewer 数据 schema 版本绑定。

macOS 和 Windows 使用同一插件 bundle。发布验收必须从干净 Vault 执行手工安装、启用、打开视图和升级测试；仅在开发 Vault 中热加载成功不能视为可发布。进入 Obsidian Community Plugins 列表属于单独的外部提交流程，不作为本地实现完成的替代证据。

插件需要调用迁移或冲突解决能力时，只能在用户明确点击后，以已配置并验证版本的 session-reviewer 可执行文件、shell=false 和固定参数数组启动允许列表命令。插件不得拼接 shell 字符串、执行 Markdown 提供的命令或静默运行有写入效果的 CLI 操作。

## 5. 编辑模型

### 5.1 可编辑内容

以下内容既能在插件页面中编辑，也能直接编辑 Markdown：

- 项目目标；
- 当前阶段和当前状态；
- 下一步；
- 风险与待办；
- 关键决策的标题、原因和影响；
- 时间节点的标题、摘要、背景、变化、结果和后续。

插件中的编辑动作打开结构化表单或 Markdown 文本域。保存时通过 Obsidian Vault API 对目标文档执行结构化修改，并保留未知 frontmatter 和未知章节。

### 5.2 只读内容

以下内容由 CLI 和隐藏账本生成，在页面中只读：

- Session 起止时间和耗时；
- Token 计数；
- 模型单价、成本和占比；
- 同步状态；
- revision、cursor、哈希和证据引用；
- 验证来源的机器身份。

插件不得仅通过前端禁用输入框来保护这些字段。Markdown 解析、proposal apply 和 sync 都必须在后端验证保留字段。

### 5.3 外部编辑与刷新

- Obsidian 中直接修改 Markdown：插件监听 Vault create、modify、rename、delete 事件，去抖后重新解析。
- 代码目录中修改 Markdown：运行现有 session-reviewer sync 后，Vault 文件变化触发刷新。
- 页面编辑：先写 Vault Markdown，再由现有三方合并同步回代码目录。
- 插件不直接写代码仓库，也不绕过 Base、Project、Vault 三方合并。

## 6. 数据流与边界

~~~mermaid
flowchart LR
    A[Session JSONL] --> B[CLI 脱敏与语义 proposal]
    B --> C[项目回顾.md 和 项目历史.md]
    B --> D[隐藏 ledger.json]
    C <--> E[三方合并 Base]
    D --> E
    E <--> F[Obsidian 副本]
    F --> G[项目脉络浏览器]
    G -->|编辑人类字段| F
~~~

约束：

- 原始 Session 不进入 Obsidian 插件；
- 插件不调用模型；
- 插件只读取经过验证的 Markdown 和 ledger；
- 语义生成仍由 Skill + CLI proposal/apply 完成；
- 同步仍由确定性本地引擎完成；
- Markdown 人类字段继续使用 Base、Project、Vault 三方合并；ledger 只从 Project 单向发布，Vault 偏离时失败并要求恢复规范副本；
- ledger 不能成为绕过 Markdown 编辑合同的第二个人工数据源。

## 7. 结构解析

两个 Markdown 使用版本化 schema 和结构化解析，不能依赖脆弱的正则替换。

- 文档 frontmatter 保存 schema_version、project_id、文档类型和 revision。
- 人类字段由稳定章节与事件边界标记定位。
- 时间节点和决策使用隐藏稳定 ID 关联。
- 未知 frontmatter、未知章节和用户补充内容原样保留。
- 重复 ID、缺失边界、非法事件关联、重定向路径或保留字段变化在任何写入前失败。
- UTF-8、中文路径、CRLF/LF 和 Windows 路径差异必须有明确的规范化合同。

解析结果必须可往返：读取后不修改任何语义内容再写回，应产生相同规范字节；重复 render 和 sync 不应持续改动文件。

## 8. 冲突体验

Project 与 Obsidian 同时修改同一语义单元时：

1. 三方合并返回冲突，不静默选择任一侧。
2. 页面顶部出现“需要处理”横幅，并继续展示最近一次有效快照。
3. 冲突面板并列显示 Base、代码目录版本和 Obsidian 版本。
4. 用户可以选择代码目录版本、Obsidian 版本，或手工合并；页面在执行前显示将运行的固定 CLI 动作和受影响字段。
5. 用户确认后，插件以无 shell 的固定参数调用现有 CLI resolve 流程；CLI 重新读取三方状态、验证冲突身份、写入 Markdown并更新 Base，状态变化则拒绝旧动作并要求刷新。
6. 冲突记录保存在隐藏目录，普通阅读目录仍只有两个 Markdown。

页面必须区分“内容冲突”“数据过期”“解析失败”“同步未运行”，不能用统一的红色错误代替可行动诊断。

## 9. 旧文档自动迁移

v2 CLI 在第一次同步旧项目时自动进入迁移流程。session-reviewer sync --dry-run 只展示迁移计划，不写入；第一次不带 dry-run 的正常 sync 在同一项目锁和事务边界内执行迁移。插件如果先检测到旧 schema，只显示“需要迁移”和准确命令，不自行绕过 CLI 写文件。

1. 读取并验证全部旧实体和派生文档。
2. 将当前目标、状态、下一步、风险和关键决策映射到项目回顾.md。
3. 将 Session、timeline、里程碑、验证和决策关系合并为项目历史.md 的逆序事件流。
4. 将用量、价格、证据、稳定 ID 和同步元数据写入 ledger.json。
5. 在 Project 的 .session-reviewer/backups/<UTC timestamp>/ 创建迁移前完整快照和 manifest；该目录不发布到 Vault。
6. 在内存中完成新三件套的解析、关联、预算和路径验证。
7. 使用事务边界原子替换 Project 内容，再通过正常 sync 发布到 Vault。
8. Project、Vault 和 Base 全部验证一致后，旧文档退出正常 inventory。

迁移过程中任何一步失败：

- 不删除或覆盖旧文档；
- 不产生半套 v2 文件；
- 返回非零退出码；
- 报告具体失败实体和恢复办法，但不泄露敏感绝对路径。

迁移完成后，普通目录只显示两个 Markdown。隐藏备份保留到用户明确清理。

## 10. 空状态与降级

- 新项目：显示目标引导、空时间线和“运行第一次回顾”动作。
- 没有关键决策：说明尚未形成影响方向的决策，不制造占位决策。
- 没有用量价格：显示已知 Token，并明确成本“无法计算”及缺失单价，不按零成本处理。
- 插件未安装或禁用：两个 Markdown 仍能独立阅读和编辑，核心信息不依赖交互页面。
- ledger 暂时不可用：展示最近一次有效快照和过期提示；不把未知统计显示为当前值。
- 大项目：时间节点列表分页或虚拟化，搜索和筛选不要求一次渲染全部历史。

## 11. 安全与隐私

- 插件不读取原始 Codex Session 文件。
- Markdown 中的 HTML、链接和 Mermaid 按 Obsidian 安全渲染合同处理，不执行用户文本中的脚本。
- ledger 在解析前验证 schema、大小上限、项目身份、相对路径和引用完整性。
- 页面默认不展示证据原文、绝对路径、令牌、高熵字符串或敏感工具输出。
- 页面编辑只能修改允许的人类字段。
- 文件读取、写入、迁移和备份继续使用根目录固定、符号链接、junction、reparse point 防护和原子写。

## 12. 测试与验收

### 12.1 Go 引擎

- v2 Markdown 与 ledger 的 schema、往返和确定性测试；
- 旧文档到两文档结构的完整、空数据、重复身份和损坏输入迁移测试；
- 保留字段、人类字段和未知章节编辑边界；
- 三方合并、冲突解决、重命名和删除；
- 迁移、apply、sync 和恢复的全计划失败关闭；
- accounting 多模型 Token、公开单价、逐模型成本、总成本和占比；
- Unicode、CRLF、长路径、符号链接、junction 和 Windows reparse point；
- 重复 apply 与 sync 无字节、哈希或修改时间漂移。

### 12.2 Obsidian 插件

- 时间节点点击切换正确详情；
- 项目演进、关键决策、投入统计三视角切换；
- 决策反向跳转到关联节点；
- workspace state 恢复选中节点；
- 页面编辑精确写回对应 Markdown 单元；
- Vault 外部修改后去抖刷新；
- 解析失败显示旧快照和可行动诊断；
- 冲突三版本对照和解决动作；
- 键盘导航、焦点、窄窗口和长文本；
- 不执行 Markdown 中的脚本或未信任 HTML。

### 12.3 真实验收

在真实 SessionReviewer 项目和已配置 Vault 上：

1. 先运行 sync --dry-run，确认无 malformed、conflict、blocked 或路径问题。
2. 执行旧文档迁移，验证 Project 普通目录只剩两个 Markdown，隐藏备份完整。
3. 执行正式 sync，再次检查 status 和 dry-run 均收敛为零操作。
4. 在 Obsidian 中点击至少五个时间节点，核对右侧背景、变化、结果、决策和下一步。
5. 切换决策和统计视角，核对反向跳转、总耗时、Token、总成本和模型占比。
6. 在插件页面编辑一个节点，在代码目录编辑另一个节点，分别同步并验证双向到达。
7. 制造同字段冲突，验证不覆盖、旧快照可读、三版本可比较并能完成解决。
8. 在 macOS 与 Windows Obsidian Desktop 上重复安装、打开、编辑和同步核心路径。

静态 HTML、组件快照、测试名称或单纯“构建成功”都不能替代真实点击与真实文件回写。

## 13. 范围外

- 本阶段不提供独立云服务或团队共享数据库。
- 本阶段不在代码编辑器中复制一套交互前端；代码侧以两个 Markdown 为可编辑降级界面。
- 插件不后台扫描原始 Session，也不自行调用模型。
- 不自动执行 Git commit、push、reset、checkout 或删除迁移备份。
- 不把所有证据和机器字段重新暴露到人类页面。
- 不维持旧的多目录、多索引、多详情文件作为第二套正常输出。

## 14. 完成标准
